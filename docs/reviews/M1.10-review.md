# M1.10 review: container images and first deployment

Goal of this step: every part runs from images, configured only by environment variables and the Config Server; on the host only HTTPS is public; data survives restarts; a crashed container comes back by itself; releases and rollbacks are one commit's images; backups are encrypted and off the host. Decision D-15 (zero budget): Oracle Cloud Always Free + a laptop tunnel fallback. Config PR: chhavinath-bit/gridreserve-config#9 (merge it first; it still needs the prod public key from the host). **Status:** everything is built and rehearsed locally; the real host is your next step (`docs/deploy/oracle.md`).

| SPA fallback, cache headers | Unknown path → `index.html`; hashed assets cached a year | Reloads on `/bookings` work; no stale app | `frontend/deploy/Caddyfile` |
| Registry and SHA tags | GHCR stores images; tag = commit | Exact releases, rollback = older tag | CI images job, `scripts/prod/release.sh` |
| CD over SSH | `workflow_run`, deploy-only key, pinned host key, smoke test from outside | A merge to `main` goes live safely | `.github/workflows/deploy.yml` |
| Backups | `pg_dump`, checksums, rclone crypt, off-site, restore drill | Data outlives the VM | `infra/backup/`, `scripts/prod/restore-drill.sh` |
| Profile files merge maps | A later profile adds map entries instead of replacing the map | Why the dev public key moved out of `application.yml` | config repo |
| Secrets created where used | `.env` generated on the host; only the public key printed | The private key never travels | `scripts/prod/init-env.sh` |

## 3. Explain it back

<details><summary>1. Why does the browser talk to Caddy and not to the gateway directly?</summary>

One public address for the app and the API: the refresh cookie can stay `SameSite=Strict` and no CORS is needed. Caddy also does TLS with automatic certificates and serves static files, things a Java gateway shouldn't spend memory on. The gateway, Eureka and the services stay unreachable from the internet (PLAT-01).
</details>

<details><summary>2. Why did the dev public key have to move out of <code>application.yml</code>?</summary>

Spring merges profile files; for a map it adds entries. With the dev key in the shared file, prod would have trusted `dev-2026-11` as well as its own key, so anyone holding the dev private key (every developer's `.env`) could sign tokens prod accepts. Each profile now lists only its own keys; the rehearsal showed a dev-signed token gets 401 in prod.
</details>

<details><summary>3. How do you roll back a bad release, and what happens to the data?</summary>

Run the Deploy workflow by hand with the previous commit SHA (the host's `.env` keeps it as `PREVIOUS_IMAGE_TAG`). Its images are still in GHCR, `release.sh` pulls them and restarts. Data lives in Docker volumes, which a release never touches. A rollback across a database migration would need a forward fix instead (Flyway migrations are never undone, CLAUDE.md §8.1).
</details>

<details><summary>4. The VM is gone. What do you need to get the data back?</summary>

The encrypted backups in Google Drive and the two `RCLONE_CRYPT_*` values you saved in a password manager. Then: new VM, `init-env.sh`, put the saved values in `.env`, Google token, deploy, `restore.sh` (it fetches and decrypts from Drive). Without the saved values the backups are unreadable, which is the point of encrypting them.
</details>

<details><summary>5. Why does the backup container become unhealthy, and why is that useful during a release?</summary>

After a failed attempt or when the last good backup is older than 26 hours. `release.sh` runs `docker compose up --wait`, which waits for every container to be healthy, so a broken backup setup (an expired Google token, say) fails the release visibly instead of silently losing backups for weeks. The rehearsal showed exactly that.
</details>
