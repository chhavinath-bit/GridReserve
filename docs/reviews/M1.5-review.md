# M1.5 review: booking engine core (hold, confirm, cancel)

Goal of this step: through the gateway, a member holds a slot for 5 minutes, confirms it, or cancels it; an admin can cancel any booking. PostgreSQL's exclusion constraints decide every overlap, so a conflict is always a clear `409`, never a `500`. Decision: D-11 (deadlock retry with Spring 7 `@Retryable`). REQUIREMENTS v0.11 clarifies FR-BK-03/04.

## 0. Learn first

New in this milestone. The full list is in [docs/learning/phase-1.md](../learning/phase-1.md) (rows tagged M1.5).

| Concept | What it is | Why here | Where |
|---|---|---|---|
| Row locks `FOR SHARE` / `FOR UPDATE` | `FOR SHARE`: many readers may hold it, writers wait. `FOR UPDATE`: one holder only. Both last until the transaction ends | Venue and bookable `FOR SHARE` so a deactivation can't slip in during a hold (CONC-09); member `FOR UPDATE` so one member's holds run one at a time (BR-08 in M1.7) | `VenueRepository`, `BookableRepository`, `MemberRepository` |
| Lock order and deadlocks | Two transactions locking the same rows in opposite orders wait for each other; PostgreSQL kills one (`40P01`). One global order prevents it | venue → bookable → member → booking rows by id | `BookingTransactions.hold`, `BookingRepository.lockStaleHolds` |
| Conditional UPDATE (`@Modifying`) | `UPDATE … WHERE id = ? AND status = 'HELD' AND expires_at > :now` returns 1 or 0 rows: a compare-and-set in SQL | Two clicks on "confirm", or confirm racing expiry: exactly one wins | `BookingRepository.confirm`, `cancel`, `expireHolds` |
| `saveAndFlush` + constraint name mapping | Sends the INSERT now so the violation can be caught; the constraint's name picks the error code | `ex_booking_bookable_overlap` → `409 SLOT_TAKEN`, `ex_booking_member_overlap` → `409 MEMBER_OVERLAP`; unknown names stay `500` | `BookingTransactions.hold`, `ConstraintViolations` |
| `23P01` and Hibernate | Hibernate fills the constraint name for unique/check/FK errors but not for exclusion violations; we read it from PostgreSQL's message with Hibernate's own template | Found by the first test run (500 instead of 409) | `ConstraintViolations.constraintName` |
| `noRollbackFor` | A thrown exception normally rolls back the transaction; this keeps the writes | Confirm after expiry saves `EXPIRED` and still answers `409 HOLD_EXPIRED` | `BookingTransactions.confirm`, `cancel` |
| `Propagation.MANDATORY` | The method fails unless a transaction is already running | A lock outside a transaction would be released immediately | `CatalogService.lockForBooking`, `MemberLock.lock` |
| Spring 7 `@Retryable` + `@EnableResilientMethods` | Built-in method retry (no extra library) on chosen exceptions, with delay and jitter | Reruns a transaction PostgreSQL killed for a deadlock; never a business refusal | `BookingService`, `config/RetryConfig` |
| Why two classes (`BookingService` → `BookingTransactions`) | Spring adds `@Retryable` and `@Transactional` through proxies; calling across beans makes the retry wrap the whole transaction | Each attempt is a brand-new transaction | `BookingService` |
| `authentication.getName()` = `sub` | For a JWT, the principal name is the `sub` claim (identity user ID) | The owner is always the caller; no endpoint takes a member ID (FR-ROLE-05) | `Viewer.memberId` |
| `ResponseEntity.created(uri)` | `201 Created` with a `Location` header | FR-BK-01 | `BookingController.hold` |
| `cast(:x as Instant) is null` | PostgreSQL can't type a bare `? is null` parameter (`42P18`) | Optional `from`/`to` filters on `/bookings/me` | `BookingRepository.findMine` |
| `Instant.truncatedTo(MICROS)` | PostgreSQL keeps microseconds, Linux clocks nanoseconds | The 201 shows the same `createdAt` a later read returns (found in the Compose check) | `BookingTransactions.hold` |
| Movable test clock | Real time + an offset the test moves | A 5-minute hold runs out instantly in a test | `support/MovableClock` |
| `@SpringJUnitConfig` + `@MockitoBean` | A tiny Spring context with chosen beans, some mocked | `@Retryable` exists only on Spring proxies, so a plain Mockito test can't prove it | `BookingRetryTest` |

## 3. Explain it back

<details><summary>1. Java checks the rules before the INSERT. Why can two members still both reach the INSERT for the same slot, and what stops a double booking?</summary>

The checks read data without blocking other bookings of the slot (the bookable lock is `FOR SHARE`, shared). Two requests can pass them at the same moment. The exclusion constraint `ex_booking_bookable_overlap` is checked inside PostgreSQL at INSERT: the second insert waits for the first transaction, then fails with `23P01`, which becomes `409 SLOT_TAKEN`. The Java checks give friendly early answers; the database gives the guarantee.
</details>

<details><summary>2. Why does confirming an expired hold need <code>noRollbackFor</code>?</summary>

We want two things: save `EXPIRED` and answer `409 HOLD_EXPIRED`. The answer is an exception, and by default a runtime exception rolls the transaction back, which would undo the `EXPIRED`. `noRollbackFor = DomainException.class` commits the write and still sends the error.
</details>

<details><summary>3. Why is <code>@Retryable</code> on <code>BookingService</code> and <code>@Transactional</code> on a different class?</summary>

Both work through Spring proxies. When `BookingService` calls `BookingTransactions`, the call passes the transaction proxy, so each call is a new transaction. If both annotations sat on one method, the retry could run inside the same (already failed) transaction, depending on proxy order. A killed transaction can't be reused; the retry must start a fresh one.
</details>

<details><summary>4. How can a deadlock happen here, and what prevents it?</summary>

Hold creation expires run-out holds in two groups: on the bookable and of the member. Two holds could each lock one stale row and then want the other's. Locking both groups in one statement `ORDER BY id FOR UPDATE` makes every transaction take those rows in the same order, so the wait can't form a circle. The retry is only a safety net; M1.8 counts deadlocks (target 0).
</details>

<details><summary>5. A member asks for another member's booking. Why 404 and not 403?</summary>

403 would confirm that booking ID exists. 404 says nothing, so IDs can't be probed (FR-ROLE-04). Admins get the booking because they may see and cancel any.
</details>

## 4. Not proven yet

- Only BR-01, 05, 06 and 09 are checked. Opening hours, grid, durations, horizon (BR-02, 03, 04, 07) and the per-member limit (BR-08) come in M1.7, so for now a hold at 03:00 or 7 hours long is accepted. The cancellation cutoff (CXL-02..04) is also M1.7.
- No hold-expiry job yet (M1.7). Run-out holds are cleaned up lazily: at confirm, at cancel, and when they block a new hold. Availability already ignores them (M1.4).
- No concurrency test yet: the 50-parallel-requests proof, member-limit races and deactivation races are M1.8. The retry is proven with a mocked deadlock, not a real one.
- No idempotency key (M1.12), no audit rows (M1.12), no admin list `/admin/bookings` (M1.11).
- Hold duration is a constant (5 minutes, A-04), not configuration.
