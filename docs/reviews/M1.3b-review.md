# M1.3b review: refresh tokens, logout, register logs in

Goal of this step: a user stays logged in until 7 days without use or until logout, without typing the password again; registering logs the user in; another site cannot use the cookie to refresh or log out. Design: one opaque token per login, stored as SHA-256, not rotated (D-37).

## 0. Learn first

New in this milestone. The full list is in [docs/learning/phase-1.md](../learning/phase-1.md) (rows tagged M1.3b).

| Concept | What it is | Why here | Where |
|---|---|---|---|
| Refresh token, sliding expiry | A long-lived secret in a cookie that buys new 15-minute access tokens. Each use moves its expiry to now + 7 days. | Stay logged in without storing the access token anywhere but memory | `RefreshTokenService`, `V3__refresh_token.sql` |

| `Optional` chains | `flatMap` / `filter` / `map` run only while there is a value | The refresh decision in one readable line | `AuthService.refresh` |
| `ResponseEntity`, `ResponseCookie` | Choose status and headers in a controller; build a `Set-Cookie` header | Login, register and refresh return a body **and** a cookie | `AuthController` |

## 3. Explain it back

<details><summary>1. Why is the refresh token stored as a hash, and why SHA-256 instead of BCrypt?</summary>

If the table leaks, hashes cannot be used as cookies. BCrypt exists for passwords people choose, which can be guessed, so it is slow and salted. Our token is 256 random bits; guessing is hopeless, so slowness adds nothing. And we must *find* the row by the token, which needs the same hash every time (no salt) and an index.
</details>

<details><summary>2. How does "logged out after 7 days without use" happen, with no timer or job?</summary>

Every refresh runs `UPDATE … SET expires_at = now + 7d WHERE token_hash = ? AND expires_at > now`. While the user is active the date keeps moving. After 7 quiet days the `WHERE` no longer matches, 0 rows change, and the answer is 401. The cookie's `Max-Age` runs out at the same time, so the browser usually stops sending it too.
</details>

<details><summary>3. Two tabs refresh at the same moment. What happens, and why is that not a race?</summary>

Both run the same `UPDATE`; both match (the token is still valid), both get 200. Nothing is rotated, so there is no "loser". `parallelRefreshesAllSucceed_FRAUTH10` proves it with 10 simultaneous calls.
</details>

<details><summary>4. Why do refresh and logout check `Origin` and `X-GridReserve-Client`, but login does not?</summary>

Refresh and logout are authenticated by the cookie, which the browser attaches even when another site triggers the request (CSRF). Login and register are authenticated by what is in the body, which another site does not know. `SameSite=Strict` already blocks most of it; the header checks are a second, independent layer.
</details>

<details><summary>5. What did we give up by not rotating the token (D-37)?</summary>

Detecting a stolen token: with rotation, a copied token used after the real one shows up as "reuse". Here a copied cookie works until logout or 7 idle days. We accepted that for a simpler design (no families, no race, no job); `HttpOnly` + `SameSite=Strict` make copying it hard, and logout really deletes it.
</details>
