# M1.13c review: members see why a booking was cancelled

Goal of this step: a member whose booking was cancelled, by themselves or by an admin, sees who did it, when and why. Decision D-49. One field added to the booking API (`cancelReason`), no migration (the column existed since V2), no config-repo change.

## 3. Explain it back

<details><summary>The reason was already stored. Why couldn't members see it?</summary>
The `cancel_reason` column and the audit row had it, but `BookingResponse`, the DTO every booking endpoint returns, didn't include it, and the UI never showed `cancelledBy` or `cancelledAt` either. DTOs decide what leaves the service; adding a field there is the whole backend change.
</details>

<details><summary>Can another member read my cancellation reason?</summary>
No. `GET /bookings/me` lists only the caller's bookings, and `GET /bookings/{id}` answers 404 for someone else's booking (FR-ROLE-04). Only the owner and admins see it, through the same checks as the rest of the booking.
</details>

<details><summary>Why trim the reason on the server when the UI already trims it?</summary>
The server can't trust the client: another client, or curl, could send "   ". Normalizing in `CancelRequest` means stored data is always clean, and "no reason" is always null, never a blank string.
</details>

<details><summary>Why one reason box for admins, not a public reason and a private note?</summary>
Owner decision: two boxes means a new column, more UI and a choice for the admin every time. One box, clearly labelled "shown to the member", is honest and simple. The audit history keeps the same text.
</details>
