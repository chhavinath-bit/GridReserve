# M1.8 review: concurrency proof (single and two instances)

Goal of this step: prove under real parallel load that double-booking is impossible, first inside booking-service, then through the gateway with two booking-service instances (PROJECT.md §8). The tests found two real problems, both fixed: a **deadlock** in hold creation and an unintended **bulkhead** at the gateway. Decision: D-41. Config repo PR: chhavinath-bit/gridreserve-config#7 (merge it first).

## 3. Explain it back

<details><summary>1. 50 requests pass every Java check for the same slot at the same moment. What stops two bookings?</summary>

The exclusion constraint `ex_booking_bookable_overlap`. The checks read before anyone has committed, so they all pass; the insert is where PostgreSQL decides. With the bookable locked `FOR UPDATE`, the 50 inserts happen one after another: the first commits, each later one fails the constraint with `23P01`, which becomes `409 SLOT_TAKEN`.
</details>

<details><summary>2. Why did <code>FOR SHARE</code> on the bookable deadlock, and why does <code>FOR UPDATE</code> fix it?</summary>

With a shared lock, many holds proceed together into the INSERT. Two of them can each add their index entry and then find the other's not-yet-committed entry in the exclusion check, so each waits for the other to finish: a cycle. PostgreSQL kills one after a second. With an exclusive lock only one hold per bookable reaches the INSERT at a time, so the cycle can't form. Holds on other bookables are unaffected.
</details>

<details><summary>3. How do you know both instances really took part, not just that two were running?</summary>

Each instance counts the holds it decided (`gridreserve.bookings.created` + `conflicts`). After the 20 rounds the test reads both counters inside the containers: both are above zero (they were 500/500, round robin). Just checking Eureka would only prove they were registered.
</details>

<details><summary>4. Why turn off a bulkhead, a resilience pattern?</summary>

It wasn't one we designed: Spring Cloud CircuitBreaker adds a 25-call bulkhead to every gateway route by default. At 50 parallel holds it rejected half, those rejections counted as failures, and the circuit breaker then refused everything for 30 s, so a normal burst became an outage. Our design (ARCHITECTURE §10) puts bulkheads on each service's outbound calls (M1.9); the gateway is protected by the circuit breaker and the time limiter.
</details>

<details><summary>5. Why assert deadlocks with an app counter instead of PostgreSQL's <code>pg_stat_database.deadlocks</code>?</summary>

PostgreSQL reports that counter from each connection lazily; a pooled connection can report seconds later, so a test reading right after the run can miss deadlocks and pass wrongly. The app counter increments at the moment a transaction is killed. The system test still prints PostgreSQL's number as a cross-check.
</details>
