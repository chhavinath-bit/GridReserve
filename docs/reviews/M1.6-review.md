# M1.6 review: thin vertical slice (frontend through the gateway)

Goal of this step: in a browser, through the gateway: log in → category → venue → bookable → date → slot → hold (5-minute countdown) → confirm → My bookings. Plain UI, but only design tokens and shared components, in light and dark. Decision: D-UI-3 (the approved package subset). No backend change.

## 0. Learn first

New in this milestone. The full list is in [docs/learning/phase-1.md](../learning/phase-1.md) §10 (rows tagged M1.6). You know React already; these are the parts that may be new or done differently here.

| Concept | What it is | Why here | Where |
|---|---|---|---|
| Vite proxy | The dev server forwards `/api` to the gateway | One origin in dev: no CORS, the refresh cookie (path `/api/v1/auth`) is sent automatically, and `Origin` stays `http://localhost:5173`, which identity checks | `vite.config.ts` |
| Access token in memory | A module variable in `api/client.ts`, never `localStorage` | An XSS script can't read a stored copy; a reload loses it and the `HttpOnly` cookie restores it (FR-UI-07) | `api/client.ts` |
| Single-flight refresh | Concurrent `401 TOKEN_EXPIRED` answers share one refresh promise, then retry once | Five parallel requests don't start five refreshes | `refreshSession`, `client.test.ts` |
| TanStack Query keys and invalidation | A key names server data; `invalidateQueries` refetches every view of it | After a hold, a 409 or a cancel, availability and My bookings refresh | `api/queryKeys.ts`, `SlotPickerPage` |
| Tailwind 4 + CSS variables | Tokens on `:root` / `.dark`, mapped by `@theme inline` to `bg-primary` etc. | One switch of `.dark` re-themes everything; no raw colors in components | `styles/globals.css` |
| shadcn/ui on Radix, `cva` | Component code copied into our repo; Radix supplies keyboard/ARIA; `cva` declares variants | We own and can change every component; looks are variants, not ad-hoc classes | `components/ui/*` |
| `Intl.DateTimeFormat` with `timeZone` | Formats an instant in the venue's zone | Times always in venue time, whatever the browser's zone (FR-UI-04) | `lib/time.ts` |
| Clock-skew-safe countdown | Deadline = arrival time + (`expiresAt` − `createdAt`) | A device clock 5 minutes off would otherwise show a wrong countdown | `features/bookings/hold.ts` |
| Pure render, `useNow` | Render must not read `Date.now()`; time comes from state updated by a timer | Enforced by `eslint-plugin-react-hooks` 7; found 3 cases on the first lint run | `lib/useNow.ts` |
| Roving tabindex + ARIA | One grid cell in the Tab order, arrows move; `aria-pressed`, `aria-disabled`, live regions | Full keyboard path; state in words, not only color (§7) | `SlotGrid`, `HoldTimer` |
| Vitest, RTL, fake `fetch` and timers | Tests in jsdom; find elements by role and name; fake network and clock | The client's refresh logic and the countdown are tested without a server or waiting | `*.test.ts(x)` |

## 3. Explain it back

<details><summary>1. Why keep the access token in memory and not in localStorage?</summary>

Anything in localStorage can be read by any script on the page, so one XSS bug leaks the token. In memory it exists only inside our module while the tab is open. The price is losing it on reload, which the `HttpOnly` refresh cookie solves: JavaScript can't read that cookie at all, and refresh needs our `Origin` and `X-GridReserve-Client` header (CSRF defence).
</details>

<details><summary>2. Five requests get 401 TOKEN_EXPIRED at the same moment. What happens?</summary>

The first starts `POST /auth/refresh` and stores the promise; the other four find it and await the same promise. One refresh, then each request retries once with the new token. If the refresh fails, the session ends and the app goes to login with `returnTo`.
</details>

<details><summary>3. Availability said FREE, the hold answered 409. Is that a bug?</summary>

No. Availability is a read that can be stale a moment later; the database decides at insert. The UI treats it as normal: show "just taken", drop the selection, refetch availability (FR-UI-05).
</details>

<details><summary>4. Why compute the countdown from <code>expiresAt − createdAt</code> instead of <code>expiresAt − now</code>?</summary>

`now` is the device clock, which can be minutes off; `expiresAt` is server time. The difference of two server times is the hold's real length (5 minutes); adding it to the moment the answer arrived gives a correct countdown on any device. The server still decides: a late confirm gets 409.
</details>

<details><summary>5. Why does the lint rule forbid <code>Date.now()</code> in render?</summary>

React may render a component more often than you expect (StrictMode, concurrent rendering); render must give the same output for the same props and state. Reading the clock breaks that. Time belongs in state, updated by an effect's timer (`useNow`, `HoldTimer`).
</details>
