# M1.13b review: a city list instead of a free-text city

Goal of this step: a venue's city can only be one of a curated list, so "Delhi", "delhi " and "claud" can't become three places in the Browse filter. The city also decides the venue's country and time zone. Decision D-48 (supersedes the city part of D-46). Migration V7, a small API change, no config-repo change.

## 0. Learn first

New in this step. The full list is in [docs/learning/phase-1.md](../learning/phase-1.md) (rows tagged M1.13b).

| Concept | What it is | Why here | Where |
|---|---|---|---|
| Reference data vs free text | Values people filter by live in a seeded table and are picked by ID | One spelling per city, by construction | `city` table (V7) |
| Composite FK onto a unique key | An FK may target any UNIQUE column set, not just the primary key | Venue's copied country and zone must equal its city's | `fk_venue_city`, `uq_city_id_country_zone` |
| Unique expression index | `UNIQUE INDEX … (country_code, lower(name))` | "delhi" can't sit next to "Delhi"; constraints can't hold expressions | `uq_city_country_name` |
| Data migration (backfill) | Add nullable column → fill with `UPDATE … FROM` → `SET NOT NULL`; `DISTINCT ON` keeps one row per group | Link V6's text cities without losing a venue | `V7__city_reference.sql` |
| Denormalized copy kept honest | Keep `country_code`/`time_zone` on venue, enforced equal by the FK | Every rule check reads the zone without a join | `Venue.update` |
| Testing a migration on old data | Flyway Java API, `target("6")`, scratch database | Prove the backfill on rows a fresh database never has | `CityMigrationIT` |

## 3. Explain it back

<details><summary>Why a table instead of trimming and title-casing the typed text?</summary>
Normalizing fixes only case and spaces. "Dilli", "New Delhi" vs "Delhi", and junk like "claud" stay possible. A list makes the valid values data that someone curated once, and the filter can key on IDs.
</details>

<details><summary>The venue still has country_code and time_zone columns. Isn't that duplication?</summary>
Yes, on purpose: every availability and booking rule reads the venue's zone, and the copies avoid a join there. The composite foreign key `(city_id, country_code, time_zone) → city (id, country_code, time_zone)` makes a copy that disagrees with the city impossible, so the duplication can't drift.
</details>

<details><summary>Why is `uq_city_country_name` an index and not a constraint?</summary>
A UNIQUE constraint lists plain columns; `lower(name)` is an expression, which only an index can hold. PostgreSQL still reports the index name as the violated constraint, so mapping errors by name keeps working.
</details>

<details><summary>What does V7 do with a venue whose typed city isn't in the list?</summary>
It adds that city once per country (case-insensitive, the oldest venue's zone) and links the venue, so no venue is lost or left without a city. `CityMigrationIT` proves it on a scratch database migrated to V6 first. In your dev database this happened to "Lakeside Courts", whose city was `Unknown`.
</details>

<details><summary>Why `/countries/{code}/cities` and not `/cities?country=`?</summary>
It sits next to `/countries/{code}/time-zones`, matches how the form works (country first), and is already covered by the gateway route `/api/v1/countries/**`, so no config-repo change was needed.
</details>

## 4. Not proven yet

- Only 67 cities are listed. A venue in an unlisted city needs a migration first; there's no admin screen to add cities.
- The local `Unknown` city stays until it's fixed by hand.
- Unknown JSON fields (for example an old client still sending `city`) are only refused after M1.14 (API-02). Until then such a request fails anyway because `cityId` is required.
- Not deployed yet: the live site gets V7 with the next deploy. If its database has venues with typed cities that aren't in the list, V7 adds those as cities, as it did locally. Check the live city list after deploying.
