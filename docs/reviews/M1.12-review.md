# M1.12 review: idempotency and audit log

Goal of this step: pressing "Hold" again after a lost answer, or two tabs sending the same request, never books twice (`Idempotency-Key`, IDEM-01..07, CONC-08); every booking change is recorded with who made it, in the same transaction, and admins can read it (FR-AUD-01..03). Decision D-44 (all five recommendations approved). One migration (V5), no config-repo change.

## 0. Learn first

New in this milestone. The full list is in [docs/learning/phase-1.md](../learning/phase-1.md) (rows tagged M1.12).

| Concept | What it is | Why here | Where |
|---|---|---|---|
| Idempotency keys | Client-chosen ID per intent; the server remembers the answer | A retried hold must not book twice | `IdempotencyService` |
| Three-step design | Claim (own tx) → hold + store answer (one tx) → store refusal or release | Duplicates see "in progress" at once; answer and booking commit together; a crash's lease runs out | `BookingService.hold` |
| `INSERT … ON CONFLICT DO NOTHING` | Insert only if free; the loser gets 0 rows, no error | Race-free claim (CONC-08) | `IdempotencyRecordRepository` |
| Leases | "In progress until T"; after T another request may take over | A crashed first request doesn't block the key for 24 h | `takeOver` |
| Retry only what can be retried | The deadlock retry moved to its own bean | A retried claim would meet its own key | `RetriedTransactions` |
| `jsonb` | PostgreSQL JSON column | The stored response body | `IdempotencyRecord` |
| `Propagation.MANDATORY` | Refuse to run without the caller's transaction | An audit row can't be written apart from its change | `AuditService.record` |
| `@Lock(PESSIMISTIC_WRITE)` | `FOR UPDATE` from Spring Data | Cancel's recorded "from" status is exact | `BookingRepository.lockById` |
| Foreign key without cascade | Deleting a booking with history fails | History can't vanish | `V5__…sql`, `TestBookings` |
| `crypto.randomUUID()` + `useRef` | Key made in the browser, kept between renders | Retry sends the same key | `SlotPickerPage`, `lib/idempotency.ts` |

## 3. Explain it back

<details><summary>1. Why is the key claimed in its own transaction, and the answer stored in the hold's?</summary>

The claim must be visible to a parallel duplicate at once: committed on its own, the duplicate sees "in progress" and gets 409 instead of trying to book too. The answer must commit with the booking: if they were separate, a crash between them would leave a booking without a stored answer (a retry would book again) or an answer without a booking.
</details>

<details><summary>2. Without idempotency, two identical holds still can't both succeed. So what does it add?</summary>

The exclusion constraint already stops a double booking, but the second request would answer `409 SLOT_TAKEN` (or `MEMBER_OVERLAP`) to the person who actually got the slot: they'd think they lost it. With the key, the retry gets the first answer: "201, here is your hold". It also makes the answer stable for refusals (the same 409 again, even if the slot freed up meanwhile, because a new attempt should be a new key).
</details>

<details><summary>3. What happens if the server crashes after claiming the key?</summary>

The record stays IN_PROGRESS with a 30-second lease. Within the lease a retry gets `409 IDEMPOTENCY_IN_PROGRESS` (the frontend keeps the key and offers Retry). After it, the next retry takes the key over (a conditional UPDATE, so only one wins) and books. If the original was in fact still running, the exclusion constraint stops a second booking.
</details>

<details><summary>4. Why did the deadlock retry have to move?</summary>

It wrapped all of `BookingService.hold`. With the claim inside, a deadlocked attempt would retry the claim, find its own key IN_PROGRESS and answer 409 to itself. Now only the hold's transaction is retried (`RetriedTransactions`), which is exactly the part PostgreSQL killed.
</details>

<details><summary>5. Why is an expiry recorded as SYSTEM even when a member's confirm found it?</summary>

The member didn't end the hold, the clock did; the member's request only noticed it. Recording the member would make the history say they expired their own hold. Same for a hold swept aside when someone else books the slot.
</details>

## 4. Not proven yet

- The browser Retry path was tested with a mocked API (Vitest), not end to end (Playwright: M1.13).
