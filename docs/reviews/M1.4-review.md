# M1.4 review: catalog, countries and availability

Goal of this step: a signed-in user can browse categories → venues → bookables and see which slots of a bookable are free on a date. Every number (slot length, durations, buffer, hours, horizon) comes from seed data through one `RuleResolver`; there is no code path per category or type. Decisions: D-39 (whole local days, unpaginated reference lists, CAPACITY → `422 WRONG_BOOKING_MODEL`).

## 3. Explain it back

<details><summary>1. Why build slots in local time and then convert, instead of stepping through UTC?</summary>

Opening hours are a wall-clock rule ("08:00 to 22:00 in London"). Stepping in UTC would shift the grid by an hour on DST days. Building in local time and converting each slot keeps "08:00" at 08:00 all year, and the stored moments stay UTC.
</details>

<details><summary>2. Can availability say FREE and the booking still fail?</summary>

Yes. Availability is a read without locks; another member can take the slot a millisecond later. The real decision is the exclusion constraint at insert (M1.5), which turns the race into one `201` and one `409 SLOT_TAKEN`. Availability is a view, never the guard.
</details>

<details><summary>3. Why does an expired hold show FREE before the expiry job runs?</summary>

Correctness must not depend on a background job (FR-EXP-04). The query only counts a HELD row while `expires_at > now`, so a hold that ran out is free immediately, job or no job.
</details>

<details><summary>4. Why does availability call `BookingOccupancy` instead of reading the booking table?</summary>

Module rule: only the booking module owns the booking table; others use its service and DTOs. It also returns only `(start, until)`, so availability cannot leak who booked (FR-AV-05).
</details>

<details><summary>5. What is an N+1 problem and how is it avoided here?</summary>

Loading 16 bookables, then lazily loading each one's type, costs 1 + 16 queries. `@EntityGraph(attributePaths = "bookableType")` joins the types into the page query; a test counts the SQL statements (≤ 3).
</details>

## 4. Not proven yet

- Nothing books yet; TAKEN is proven with rows inserted by the tests. Hold, confirm and cancel come in M1.5.
- No admin endpoints to create or edit venues and bookables (M1.7); inactive states are set directly in the tests.
- On fall-back night the repeated local hour gets one slot that lasts two real hours (first offset to the next local hour). Documented, not a requirement yet.
- Availability marks each slot on its own; whether a whole booking (e.g. 45 min + 15 min buffer) fits is checked at booking time (M1.5), not here.
- No cache (Phase 4).
