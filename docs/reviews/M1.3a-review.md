# M1.3a review: identity core and access tokens

Goal of this step: users can register and log in, identity-service signs RS256 access tokens, and the rules for accepting a token live in one shared place that the gateway and booking-service will reuse in M1.3c.

## 0. Learn first

These concepts are new in this milestone. The full Phase 1 list, including everything from M1.1 and M1.2, is in [docs/learning/phase-1.md](../learning/phase-1.md).

| Concept | What it is | Why here | Where |
|---|---|---|---|
| Hashing and BCrypt | A one-way, deliberately slow, salted hash. `$2a$10$…` contains the cost (10) and the salt. BCrypt reads at most 72 **bytes**. | Passwords are stored only as hashes (FR-AUTH-03) | `SecurityConfig.passwordEncoder`, `V2__seed_demo_users.sql`, `Credentials.fitsBcrypt` |
| User enumeration and timing | Different answers, or different response times, reveal whether an email has an account | Login answers the same way for every failure and always runs one BCrypt check | `AuthService.login` |
| JWT and its claims | `header.payload.signature` in Base64URL. Anyone can read the payload; only the signature proves who issued it. Claims: `iss`, `aud`, `sub`, `iat`, `exp`, plus our `role`. | The access token every service will trust | `AccessTokenIssuer` |
| RS256 vs HS256 | Asymmetric: the private key signs, the public key only verifies. HS256 shares one secret that can do both. | Only identity can mint tokens; others just check them | `JwtSigningConfig`, `AccessTokenVerification` |
| PEM, X.509, PKCS#8 | Text-wrapped binary key formats: public keys in X.509, private keys in PKCS#8 | Keys arrive as text from config and `.env` | `PemKeys`, `infra/.env.example` |
| `kid` and key rotation | The key ID in the token header picks which public key verifies it | Lets us change keys without logging everyone out | config repo `gridreserve.jwt.public-keys` |
| Clock skew | Small differences between hosts' clocks | Tokens get 30 s of grace after `exp` | `AccessTokenVerification.CLOCK_SKEW` |
| Spring Security filter chain | Filters that run before controllers. A `SecurityFilterChain` bean lists the public paths and the paths that need a user. | Register and login are public; `/me` is not | `SecurityConfig` |
| Stateless auth and CSRF | No server session; a Bearer token on every request. CSRF only matters when a cookie authenticates. | CSRF is off now; the refresh cookie in M1.3b gets its own checks | `SecurityConfig` |
| Spring resource server, `JwtDecoder` / `JwtEncoder`, token validators | Spring's built-in Bearer-JWT support: the decoder verifies and parses, the encoder signs, and validators add claim rules. Nimbus JOSE does the cryptography. | Replaces hand-written token code (D-34) | `AccessTokenVerification`, `JwtSigningConfig` |
| 401 vs 403; entry point vs access-denied handler | 401 = we don't know who you are; 403 = we know you, but you may not do this. Spring calls a different handler for each. | Security errors happen before controllers, so they need their own JSON writer | `JsonSecurityErrorHandler` |
| Authorities, `ROLE_` prefix, `FACTOR_BEARER` | Permissions are strings, and roles are authorities with a prefix. Spring Security 7 also records *how* the user authenticated. | `role: ADMIN` becomes `ROLE_ADMIN` | `AccessTokenVerification.authenticationConverter` |
| `@AuthenticationPrincipal Jwt` | Injects the verified token into a controller method | `/me` takes the user ID only from the token | `MeController` |
| `@ConfigurationProperties` + `@Validated` records | Typed config bound and checked at startup | A missing key stops startup instead of breaking the first login | `JwtProperties`, `JwtSigningProperties` |
| Optional dependency + `@ConditionalOnClass` | A library a module compiles against without passing it on; the auto-config turns on only where the class exists | booking-service gets token checks only when it opts in (M1.3c) | `common-web/pom.xml`, `CommonWebSecurityAutoConfiguration` |
| `@Transactional`, `saveAndFlush`, exception translation | A transaction around a service method; flush sends the INSERT now; Spring wraps database errors in `DataIntegrityViolationException`. | The duplicate-email error must surface inside the `try` | `UserService.register`, `ConstraintViolations` |
| `ApplicationContextInitializer` | Adds properties before any bean is created | Tests generate throwaway keys, so none is committed | `TestJwtKeys` |
| Concurrency test with `CountDownLatch` | All threads are released at the same moment | Proves the unique constraint, not luck, gives one winner | `AuthFlowIT.concurrentRegistrationsOneWinner_FRAUTH02` |

## 2. Run these yourself

```bash
cd backend && ./mvnw -B verify
```
Expected: BUILD SUCCESS. identity-service shows 6 unit tests and **15** integration tests; common-web shows 20.

Through the stack (`cd infra && docker compose up -d --build --wait`), use the curl commands in README "Demo accounts and logging in". Then:

1. Paste your token into a JWT viewer, or run `cut -d. -f2 <<< "$TOKEN" | base64 -d`. You should see `sub`, `role`, `iat`, `exp`, `iss`, `aud`, and no email.
2. Change one character in the middle of the token and call `/me`. Expect 401.

Make it fail on purpose, then undo with `git checkout -- .`:
- In `AccessTokenVerification`, delete the `new ExpiryValidator(clock),` line, then run `./mvnw -pl libs/common-web test`. Which tests fail?
- In `infra/.env`, change one character inside `JWT_PRIVATE_KEY`, then run `docker compose up -d identity-service`. Read the log: startup stops, and the message must not contain the key. Restore the line afterwards.

## 3. Explain it back

<details><summary>1. Why RS256 and not a shared secret (HS256)?</summary>

With HS256, every service that verifies tokens holds the secret and could also create tokens. With RS256 only identity-service has the private key. The others hold only the public key, which can verify but not sign. One leaked service can't mint admin tokens.
</details>

<details><summary>2. How does booking-service check a token without calling identity-service?</summary>

It verifies the signature with the public key from config, then checks expiry, issuer, audience and claims locally. No network call happens, so booking keeps working while identity is down (FR-AUTH-06). The cost: a disabled user's token stays valid until it expires (at most 15 minutes, A-02).
</details>

<details><summary>3. Why does login answer the same for "no such email" and "wrong password", and why the dummy hash?</summary>

Different answers would let anyone check which emails have accounts (user enumeration). The timing must match too: BCrypt takes about 100 ms, so skipping it for unknown emails would make them answer measurably faster. Comparing against a dummy hash keeps both paths equally slow.
</details>

<details><summary>4. Why not check "email already exists" before inserting?</summary>

Check-then-insert is a race: two requests both see "free" and both insert. The unique constraint decides inside PostgreSQL. The test with 10 parallel registrations gets exactly one 201. It's the same idea as the booking exclusion constraint.
</details>

<details><summary>5. What is `kid` for?</summary>

It names the key that signed the token. To rotate keys, publish the new public key next to the old one, switch identity to sign with the new `kid`, and remove the old key after 15 minutes, when its last tokens have expired. Nobody gets logged out. A token without a `kid` is rejected, so it's always clear which key must verify it.
</details>

## 4. Not proven yet

- The gateway and booking-service don't check tokens yet (M1.3c). Today a request to booking passes without one.
- There's no refresh token or cookie (M1.3b). After 15 minutes the user must log in again.
- `/internal/**` is open inside the Docker network until service tokens arrive (D-19, M1.9).
- Equal login timing is designed in, not measured.
