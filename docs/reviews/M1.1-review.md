# M1.1 review guide: platform skeleton

For the owner to review **before merging** [GridReserve PR #2](https://github.com/chhavinath-bit/GridReserve/pull/2) and [gridreserve-config PR #1](https://github.com/chhavinath-bit/gridreserve-config/pull/1). Claude's checks in `docs/PROGRESS.md` are a first pass; this review is the verification.

Plan about 60–90 minutes: Part A (read, ~30 min), Part B (run, ~20 min), Part C (explain it back), Part D (what is *not* proven yet), then sign off.

## Part A — Read the code that carries the design

Read in this order. For each file: what to look for, and something to challenge.

| # | File | Look for | Challenge |
|---|---|---|---|

| 2 | `backend/*/*/pom.xml` (any two) | Dependencies without versions; `common-web` only in servlet services, not in the gateway | Is every dependency actually used? (e.g. validation starter in the services) |
| 3 | `libs/common-web/.../config/CommonWebAutoConfiguration.java` + `META-INF/spring/...AutoConfiguration.imports` | How shared beans reach services without component scanning; `@ConditionalOnMissingBean` | What happens if booking-service defines its own `Clock` bean? |

| 6 | `platform/config-server/src/main/resources/application.yml` + `infra/compose.yaml` (config-server) | Git backend for prod, `native` for dev via profile; read-only mount | What exactly broke with a Git `file:` URI? (PROGRESS, M1.1 problem 3) |

| 8 | `platform/api-gateway/.../RequestIdWebFilter.java`, `GatewayErrorHandler.java`, `FallbackController.java` | WebFilter vs GlobalFilter; `@Order(-2)`; `beforeCommit` to avoid a duplicate header | Why does the gateway duplicate the error record instead of using common-web? |
| 9 | `gridreserve-config/api-gateway.yml` | Route order (identity first, booking catch-all last); CircuitBreaker + `fallbackUri`; Retry **GET only** | Which statuses are retried? What would go wrong if POST were retried? |
| 10 | `services/*/src/main/resources/application.yml` | `${CONFIG_IMPORT:configserver:…}` and `fail-fast: true` | Why the placeholder instead of a plain `configserver:` import? |
| 11 | `services/booking-service/.../client/IdentityClient.java`, `IdentityClientFallback.java`, `gridreserve-config/booking-service.yml` | `@FeignClient(name = "identity-service")` = Eureka service ID; fallback; timeouts | There are two beans of type `IdentityClient`. Why doesn't injection fail? |

| 13 | `infra/compose.yaml`, `infra/postgres/init-databases.sh` | Health checks + `depends_on: service_healthy`; ports on `127.0.0.1`; booking has no host port; `restart: unless-stopped`; one DB + user per service | What happens to the init script on the second `up`? |
| 14 | `gridreserve-config/application.yml`, `application-dev.yml` | Resilience defaults (A-25); faster registry and cache refresh in dev | Why only in dev? |
| 15 | `.github/workflows/ci.yml` | What CI runs, and what it does **not** run | See Part D |

## Part B — Run it yourself

Use your own terminal, or type the command here with a leading `!`. Compare with the expected result; anything different is a finding.

### B1. Tests: check what actually runs

```bash
cd backend
./mvnw -B verify
```

Expected: `BUILD SUCCESS`, 16 tests in total. Then **open the reports and read the tests**:

```bash
ls */*/target/surefire-reports/*.txt libs/common-web/target/surefire-reports/*.txt
cat services/booking-service/target/surefire-reports/*.txt
```

Open `services/booking-service/src/test/java/.../BookingServiceApplicationTest.java` and answer for yourself: *what behavior does this test prove, and what does it not prove?*

### B2. Stack

```bash
cd infra
docker compose up -d --build --wait
docker compose ps
curl -s -H "Accept: application/json" localhost:8761/eureka/apps | grep -o '"name":"[A-Z-]*"'
curl -s localhost:8888/booking-service/dev | grep -o '"name":"[^"]*"'
```

Expected: 6 containers healthy; API-GATEWAY, IDENTITY-SERVICE, BOOKING-SERVICE registered; config sources `application-dev.yml`, `booking-service.yml`, `application.yml`. Also open http://localhost:8761 in a browser.

### B3. Routing and request IDs (wait ~15 s after B2)

```bash
curl -i localhost:8080/api/v1/ping
curl -i -H "X-Request-Id: my-test-1" localhost:8080/api/v1/ping
curl -s localhost:8080/api/v1/does-not-exist
curl -s localhost:8080/nope
```

Expected: 200 from booking-service; your ID comes back unchanged (exactly one header); both 404s in the same JSON format — one produced by booking-service, one by the gateway. Can you tell which is which from the response alone?

### B4. Failure experiments

```bash
# Feign fallback (spike S2)
docker compose stop identity-service
curl -s localhost:8080/api/v1/ping/identity          # expect "unavailable (fallback)"
docker compose start identity-service                 # wait ~20 s, then retry: real instance ID

# Gateway circuit breaker fallback (S3)
docker compose stop booking-service
curl -s -w "\nHTTP %{http_code} in %{time_total}s\n" localhost:8080/api/v1/ping   # expect 503 JSON, ~3 s
docker compose start booking-service

# Load balancing
docker compose up -d --scale booking-service=2 --wait
for i in 1 2 3 4 5 6; do curl -s localhost:8080/api/v1/ping; echo; done          # two instance IDs alternate

# Config server down at startup (S6)
docker compose up -d --scale booking-service=1
docker compose stop config-server
docker compose restart identity-service
docker compose ps identity-service                      # Restarting
docker compose logs identity-service --tail 5
docker compose start config-server                      # identity recovers on its next restart

docker compose down
```

For each experiment, write one sentence: *what failed, what the user saw, and which component made that happen.*

## Part C — Explain it back

Try to answer aloud before opening the answer. These are the questions an interviewer can ask about this milestone.

<details><summary>1. Why does the parent POM use the Spring Boot parent but import the Spring Cloud BOM?</summary>

Maven allows only one parent. The Boot parent provides managed versions and plugin configuration; Spring Cloud versions come in through `<dependencyManagement>` with `<scope>import</scope>`. Together, modules declare dependencies with no versions, and upgrades happen in one place.
</details>

<details><summary>2. How do common-web's beans get into booking-service without component scanning?</summary>

Spring Boot auto-configuration: `CommonWebAutoConfiguration` is listed in `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`. Boot loads it like its own starters. `@ConditionalOnMissingBean` lets a service replace any bean (for example a fixed `Clock` in tests).
</details>

<details><summary>3. Why is the Config Server reached by a fixed URL instead of through Eureka?</summary>

A service needs its configuration — including where Eureka is — before it can talk to Eureka. Looking up the Config Server through Eureka creates a startup cycle. A fixed `CONFIG_SERVER_URL` breaks it. For the same reason Eureka keeps its own local config.
</details>

<details><summary>4. Why is the gateway reactive (WebFlux) when the services are Spring MVC?</summary>

A gateway mostly waits on network I/O for many concurrent requests, which a non-blocking server handles with few threads. The WebFlux variant is the most widely used and has the Redis rate limiter built in (Phase 4). The gateway has almost no business code, so the reactive style stays contained; services stay with simpler blocking MVC.
</details>

<details><summary>5. Why is the request ID set in a WebFilter, not a gateway GlobalFilter?</summary>

GlobalFilters only run for routed requests. The gateway's own 404s and fallback responses also need an ID; a WebFilter runs for every request.
</details>

<details><summary>6. Which requests does the gateway retry, and why never POST /bookings?</summary>

Only GET, on 502/503, twice with backoff. A POST that timed out may have succeeded on the server; retrying it could create a second hold. The client retries instead, with the same `Idempotency-Key`, which the server deduplicates (M1.12).
</details>

<details><summary>7. Walk through what happens when booking-service calls identity-service while identity is down.</summary>

Feign asks Spring Cloud LoadBalancer for an `identity-service` instance (from Eureka's cached registry, possibly still listing the dead instance). The connection fails or hits the 1 s connect timeout; the Resilience4j circuit breaker records a failure and the fallback answers. After enough calls in the window (10 minimum, ≥ 50 % failing) the circuit opens and calls fail fast without touching the network for 30 s. When identity re-registers and the caches refresh, calls succeed again.
</details>

<details><summary>8. There are two beans of type IdentityClient. Why does injection work?</summary>

Spring Cloud OpenFeign registers the Feign proxy as `@Primary`. The fallback is a separate `@Component` that the circuit-breaker integration uses only when a call fails.
</details>

<details><summary>9. Why do the services import config through ${CONFIG_IMPORT:configserver:…}?</summary>

Tests run without a Config Server. Turning the config client off (`spring.cloud.config.enabled=false`) does not make a `configserver:` import optional — Boot can't resolve the location and refuses to start. The placeholder keeps the real import for running apps and lets tests point it at an optional empty location.
</details>

<details><summary>10. What happens if the Config Server is down when a service starts?</summary>

The service fails fast (`ConfigClientFailFastException`). It has no in-app retry; the container platform restarts it with growing back-off (`restart: unless-stopped`), and it starts normally once the Config Server is back (PLAT-07, spike S6).
</details>

<details><summary>11. Why does dev use the Config Server's native backend instead of Git?</summary>

With a Git `file:` URI the Config Server works inside the repository itself: lock files, branch checkouts, fetching from the remote. On a read-only mount that fails; on a writable mount it would change branches in your own working copy. `native` just reads the YAML files. Prod keeps the Git backend on GitHub.
</details>

<details><summary>12. Right after startup the gateway said "No servers available". Why, and why was it fixed only for dev?</summary>

Callers refresh their copy of the Eureka registry every 30 s and the load balancer caches instance lists for 35 s by default, so new instances can be invisible for up to about a minute. Dev shortens both to 5 s for fast feedback; in prod, defaults are fine because services run for a long time and frequent polling costs load on Eureka.
</details>

<details><summary>13. Which services can be scaled with --scale as configured, and what stops the others?</summary>

Any service without a published host port: booking-service and identity-service. The gateway (8080), Eureka (8761), the Config Server (8888) and PostgreSQL (5432) publish a fixed host port, and a second container would fail because the port is taken. (PostgreSQL also can't simply be scaled: it is a single database.)
</details>

<details><summary>14. What does -pl "${MODULE}" -am do in the Dockerfile?</summary>

`-pl` selects one module; `-am` ("also make") builds the modules it depends on first (for services: `common-web`). Each image compiles only what it needs.
</details>

<details><summary>15. Why is every published port bound to 127.0.0.1?</summary>

So the dev stack is reachable from your machine only, not from other devices on the same network. Services without a published port are reachable only inside the Compose network, i.e. through the gateway.
</details>

## Part D — What is NOT proven yet (by design or gap)

| Gap | Why it matters | When it is closed |
|---|---|---|
| Spikes S1–S3 and load balancing were checked **manually**; no automated test proves the Feign fallback, the gateway circuit breaker actually opening, or round robin | A future change could break them without a red build | M1.8 (two-instance test), M1.9 (resilience tests with WireMock, D-28) |
| The gateway test calls `/fallback/...` directly; it does not prove the CircuitBreaker filter routes there | Same | M1.9 |
| CI runs `./mvnw verify` only: no Docker image build, no Compose run, no system tests | Broken Dockerfile or Compose would not fail CI | M1.10 (image build), system-test job in M1.8 |
| No authentication anywhere: services, Eureka and the Config Server are open | Acceptable locally (ports on 127.0.0.1); never deployable like this | M1.3 (tokens), M1.10 (prod exposure) |
| Feign calls don't forward `X-Request-Id` | Request tracing stops at the first service-to-service call | M1.9 |
| `/api/v1/ping` and `/internal/ping` are temporary | Must not remain in real APIs | Removed when real endpoints exist (M1.4–M1.5) |
| Spring Cloud LoadBalancer default cache (warning in gateway log) | Fine for dev, not recommended for production | Decide before M1.10 |
