# M1.7 review: all booking rules and hold expiry

Goal of this step: every Phase 1 booking rule is enforced on the server in the documented order, the cancellation cutoff applies, and run-out holds are cleaned up by a background job that is safe on any number of booking-service instances. Decisions: D-40 (whole-day horizon for holds too, `cancellableUntil`, limit by the category's bookable IDs). REQUIREMENTS v0.12.

## 0. Learn first

New in this milestone. The full list is in [docs/learning/phase-1.md](../learning/phase-1.md) (rows tagged M1.7).

| Concept | What it is | Why here | Where |
|---|---|---|---|
| Wall clock vs elapsed time | Hours and grid read the local clock (`ZonedDateTime`); length is real time (`Duration.between`) | On a DST day they differ; each rule uses the right one | `BookingRules` |
| `FOR UPDATE SKIP LOCKED` | Lock a row, but skip rows someone else holds instead of waiting | Two job instances share the run-out holds without blocking or double-processing | `BookingRepository.lockRunOutHold` |
| One transaction per item | The job commits after every hold | A crash or shutdown mid-run leaves no half-done work; P3 will add waitlist promotion in the same per-hold transaction | `HoldExpiryService.expire` |
| Policy in the conditional UPDATE | The cancellation rules are part of the `WHERE` | Check and change are one atomic step; a confirm racing a cancel can't slip past the cutoff | `BookingRepository.cancel` |
| `SchedulingConfigurer`, fixed delay | Register a job in code with a typed `Duration`; the next run starts N seconds after the last ended | No overlapping runs; the interval comes from validated properties; tests switch it off | `HoldExpiryJob` |
| `@DefaultValue` on a properties record | Defaults on the record itself; "30s" is converted to a `Duration` | A missing `enabled` would otherwise bind as `false` and silently disable the job | `HoldExpiryProperties` |
| Micrometer counter with a tag | `gridreserve.holds.expired{layer=…}` | Shows which of the three expiry layers does the work | `HoldExpiryMetrics` |
| `@RepeatedTest(20)` | One test run 20 times | The concurrency test's 20 runs happen in every build, CI included | `HoldExpiryJobIT` |
| Switch expression over an enum | Every constant must be handled | A new booking status is a compile error in `cancellableUntil` until decided | `BookingMapper` |

## 3. Explain it back

<details><summary>1. Two booking-service instances run the expiry job at the same moment. Why is no hold expired twice, and why does neither wait for the other?</summary>

Each hold is handled in its own transaction: `SELECT … FOR UPDATE SKIP LOCKED` locks it, or returns nothing if the other instance holds it right now, so nobody waits. The UPDATE also says `WHERE status = 'HELD' AND expires_at <= :now`, so once one instance commits, the row no longer matches for the other. `HoldExpiryJobIT` runs two sweeps through a start gate, 20 times; the counts always add up to 40.
</details>

<details><summary>2. Why is the member limit counted after locking the member row?</summary>

Without the lock, two holds of the same member could both count 2 active bookings and both insert, ending at 4. With `SELECT … FOR UPDATE` on the member row, the second hold waits until the first commits, then counts 3 and is refused. That is "never check-then-write without a lock" (CLAUDE.md §8.3); M1.8 proves it with parallel requests (CONC-05).
</details>

<details><summary>3. Why put the cancellation policy into the UPDATE's WHERE instead of checking in Java first?</summary>

A Java check reads the booking, then decides, then writes: in between, a confirm could turn a HELD (always cancellable) into a CONFIRMED inside the cutoff. With the policy in the WHERE, the database checks and changes in one step; 0 rows means refused, and we read the row only to explain why.
</details>

<details><summary>4. On spring-forward night in London, is 00:00–02:00 a one-hour or a two-hour booking?</summary>

One hour of real time (01:00–02:00 doesn't exist that night). The rules use the wall clock for hours and grid (it starts at 00:00, a grid point) and real time for length (60 minutes), so with a 60-minute maximum it's accepted, and 02:00–04:00 (two real hours) is refused.
</details>

<details><summary>5. If the expiry job stopped running, what would break?</summary>

Nothing a user relies on: availability, confirm, cancel and new holds all compare `expires_at` with now (FR-EXP-04). Rows would stay `HELD` with a past `expires_at` until something touches them, and the `layer=job` metric would stop growing while `hold`/`confirm` grow, which is how you'd notice.
</details>
