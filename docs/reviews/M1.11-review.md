# M1.11 review: admin catalog management and oversight

Goal of this step: admins create and edit venues and bookables, close or reopen them without touching existing bookings, and see every booking with member names, and the list still works when identity-service is down. Backend only; the admin screens come in M1.13. Decision D-43 (one PR, `version` in the PUT body). No config-repo change and no migration.

## 0. Learn first

New in this milestone. The full list is in [docs/learning/phase-1.md](../learning/phase-1.md) (rows tagged M1.11).

| Concept | What it is | Why here | Where |
|---|---|---|---|
| PUT as full replacement | The request carries the whole editable state | Simple to validate; the admin form sends what it shows | `AdminCatalogController` |
| `List<@Valid @NotNull X>` | Bean Validation on each list element, errors named by index | Weekly hours | `CreateVenueRequest` |
| Method-specific security rules | `requestMatchers(HttpMethod.POST, …)` | Members read `/venues`, only admins write | `SecurityConfig` |
| Optimistic locking (`@Version`) | `UPDATE … WHERE version = ?`; no match → exception | Two admins editing the same thing (FR-CAT-15) | `AdminCatalogService` |
| Bulk `@Modifying` delete | One statement, run at once | Replace weekly hours without key collisions | `*OpeningHoursRepository` |
| Entity factory methods and mutators | `create`, `update`, `changeActive`, no setters | The rules of a change in one place | `Venue`, `Bookable` |
| `FieldValidationException` | Service-side checks answered like Bean Validation | Rules that need the type's defaults or the country's zones | `common-web` |
| SPI to avoid a module cycle | Catalog defines an interface, booking implements it | "How many bookings are still scheduled?" | `ScheduledBookings` |
| Soft close | Stop new bookings, change nothing existing | FR-CAT-10/13, FS-13 | `AdminCatalogService` |
| Remote call after the transaction | Read, close the transaction, then call identity once per page | No DB connection held while waiting for identity | `AdminBookingService` |
| Commit timestamps | `pg_xact_commit_timestamp(xmin)` shows when a row's transaction committed | Proves "no hold committed after the deactivation" | `DeactivationRaceIT` |

## 3. Explain it back

<details><summary>1. Why can an open hold still be confirmed after the bookable is closed?</summary>

Soft close (FR-CAT-10): closing only stops *new* bookings. The member got the hold while the bookable was open; confirming is finishing that booking, not making a new one. Confirm doesn't check `active`, cancel follows the normal policy, and the admin sees `activeFutureBookings` to know what is still coming.
</details>

<details><summary>2. A hold and a deactivation arrive together. Why can't the hold sneak in after the deactivation?</summary>

Both take the bookable's row lock `FOR UPDATE`. Whoever gets it first finishes and commits; the other waits. A hold that waited then reads the bookable *after* getting the lock and sees `active = false` → 422. The mutation test shows it: read the flag before the lock, and holds commit after the deactivation.
</details>

<details><summary>3. Why check the version yourself if Hibernate's <code>@Version</code> already refuses stale updates?</summary>

`@Version` only notices if the other save happened *between* our read and our write in this request. An admin who loaded the form ten minutes ago sends an old version; Hibernate would load the current row (current version) and happily save over the colleague's change. Comparing the client's version catches that; `@Version` catches the truly simultaneous case. Two layers, two tests.
</details>

<details><summary>4. Why is the admin list not <code>@Transactional</code>?</summary>

It calls identity-service for names. Inside a transaction, a slow identity (up to ~7 s with retries) would hold a database connection, and the pool has only 10. CLAUDE.md §6.2: no remote call inside a transaction. The page is read in its own short transaction, then identity is called once for the whole page.
</details>

<details><summary>5. Why does the catalog module get the booking count through an interface?</summary>

Booking already depends on catalog (rules, locks, names). If catalog called the booking service directly, the modules would depend on each other in a circle. The catalog defines `ScheduledBookings` ("tell me what's still scheduled"), the booking module implements it, and Spring wires them: catalog never sees booking classes.
</details>
