# M1.3c review: token checks in the gateway and booking-service

Goal of this step: no request reaches a service without a valid access token. The gateway refuses it first. booking-service checks the token, and the role, again itself, without calling identity-service. booking-service can create its local `member` row safely. Design: one set of token rules in `common-web`, used by the gateway and by every service (D-38).

## 3. Explain it back

<details><summary>1. The gateway already checks the token. Why does booking-service check it again?</summary>

The gateway is only the front door. Inside the Docker network (and later on the host) anything can call booking-service directly, so a service that trusts "the gateway must have checked" is open to anyone who gets past the door. Also only booking-service knows which of its endpoints need ADMIN. The gateway check is cheap early rejection; the service check is the real guard.
</details>

<details><summary>2. How can both check the token without calling identity-service?</summary>

The token is signed with identity's private key (RS256). Everyone else has the public key from the config repo and can check the signature, expiry, issuer, audience and claims locally. That is why booking keeps working when identity is down (RES-07), at the cost that a disabled user's token stays valid for up to 15 minutes.
</details>

<details><summary>3. Why does the gateway use common-web's rules instead of its own copy?</summary>

Two copies drift: one day someone adds a check to the services and forgets the gateway, and the two accept different tokens. One `AccessTokenVerification` means one definition of "valid". The price was making webmvc optional in `common-web`, otherwise the gateway would have started as a servlet app.
</details>

<details><summary>4. Why do the auth endpoints ignore the Authorization header?</summary>

Spring's Bearer filter checks any token it sees, even on public paths, and answers 401 for a bad one. The frontend may send its expired access token along with `/refresh`; without this, it would get `TOKEN_EXPIRED` from the very call meant to fix that. A mutation check found it: with the gateway rule set to "allow everyone", the bad-token tests still passed, which showed the filter runs on public paths too.
</details>

<details><summary>5. Why `INSERT … ON CONFLICT DO NOTHING` and not "if not exists, insert"?</summary>

Check-then-insert is a race: two first requests of the same user both see "no row" and both insert, and one fails with a duplicate key. The single statement lets PostgreSQL decide: one insert wins, the others do nothing. `parallelEnsureCreatesOneRow` starts 10 threads at once and gets exactly one creator.
</details>
