# M1.9 review: resilience patterns and configuration refresh

Goal of this step: calls between services are protected (timeouts, retry, circuit breaker, bulkhead, rate limiter) with explicit fallbacks; the platform keeps working when parts fail; configuration changes reach every instance without a restart. The first real call between services (booking → identity) is built with service tokens (D-19). Decisions: D-28 (WireMock), D-42. Config repo PR: chhavinath-bit/gridreserve-config#8 (merge it first). **New `.env` values:** `BOOKING_SERVICE_CLIENT_SECRET` and its SHA-256 (I added a generated pair to your local `infra/.env`; see `.env.example`).

## 3. Explain it back

<details><summary>1. Why is Retry the outermost decorator and Bulkhead the innermost?</summary>

Each retry attempt should be one circuit-breaker call, so the breaker sees every failure and can open; and the bulkhead should only limit actual calls in flight, rejecting at once without retries. Retry(CircuitBreaker(Bulkhead(call))) does both. The config makes sure a full bulkhead neither counts as identity failing nor gets retried.
</details>

<details><summary>2. A service token is a valid JWT signed by identity. Why can't it call <code>/api/v1/bookings</code>?</summary>

User endpoints require role MEMBER or ADMIN; a service token has role SERVICE. A valid signature only proves who issued it, not what kind of caller it is. Its `sub` is "booking-service", not a user ID, so letting it in would also break the "owner = token sub" rule.
</details>

<details><summary>3. Identity is down. What does booking do for a hold, and for the admin list?</summary>

A hold never calls identity: tokens are checked locally and booking has its own member rows, so it works. The admin list (M1.11) calls identity for names; the circuit opens after repeated failures and the fallback returns member IDs only with `memberDetailsAvailable: false` instead of failing the page.
</details>

<details><summary>4. Why did configuration refresh need our own code?</summary>

`/actuator/refresh` re-read the new threshold (the script showed the changed key), but the existing circuit breaker kept 50: Resilience4j's Spring Boot module targets Boot 3 and doesn't rebuild policies on Boot 4. `ResilienceRefresher` listens for the end of a refresh and swaps in rebuilt policies; `IdentityGateway` looks them up per call, so the next call uses the new values.
</details>

<details><summary>5. During FS-34 two reads got 503. Is that a failure?</summary>

No. A read in flight on the instance being killed can fail even after retries (with 40 parallel requests a retry can land on the dying instance again). REQUIREMENTS allows 2xx/503 there; what must hold is: never a 500, reads recover right after, and no slot is booked twice. All three were checked.
</details>
